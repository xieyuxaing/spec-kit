# 01. Feature Request

## 原始意图

自然语言需求可以概括为：

> 在每日选股控制台里增加一个状态中心，让操作者快速知道当前交易日的流程是否已经准备好复核、计划、执行和审计。

这个需求不是“再做一个漂亮卡片”。真正问题是：

- 每日流程由多个步骤组成。
- 每个步骤的数据分散在不同表、API 和文件里。
- 用户需要一个可信的只读入口判断今天能不能继续操作。
- Agent 需要从这个功能中学习如何把业务流程变成 spec。

## 需求背后的用户问题

操作者每天面对的是一个流程，而不是一个单独页面。
如果只看候选股数量，可能忽略这些问题：

- 行情数据没有更新。
- 因子没有构建。
- 当前策略缺少必要字段。
- 候选股还没有复核。
- 交易计划没有确认。
- 手工执行没有报告。
- 数据库还没有做新备份。

因此用户真正需要的是“今天这条链路走到哪一步了”。

## 适合写 spec 的原因

这个需求适合写 feature spec，因为它满足多个条件：

- 改变用户可见操作流。
- 新增 API 契约。
- 聚合 SQLite 状态和文件状态。
- 涉及交易前后的审计判断。
- 需要后端和前端一起改。
- 需要更新长期项目记忆。

如果只在聊天里描述，再直接写代码，后续 agent 很容易误解：

- 把状态中心写成自动修复按钮。
- 把 broker 或 live trading 混进状态判断。
- 漏掉备份状态。
- 漏掉策略缺字段分支。
- 忘记更新 `docs/project/api-contracts.md`。

## 需求拆解

可以把需求拆成四个问题。

第一个问题：用户要看到什么？

- 当前交易日。
- 当前策略。
- 总体状态。
- 每个流程步骤的状态。
- Tushare 积分等级。
- 其他策略是否因为缺字段不可用。

第二个问题：系统要从哪里判断？

- `daily_bars` 判断行情数据。
- `factor_values` 判断因子。
- 已有 candidate service 判断候选和策略缺字段。
- `candidate_reviews` 判断复核。
- `manual_trade_plans` 判断人工计划。
- `manual_execution_reports` 判断执行报告。
- `backups/stocks-*.sqlite` 和数据库文件 mtime 判断备份新鲜度。

第三个问题：系统不能做什么？

- 不能写数据库。
- 不能生成候选股。
- 不能确认交易计划。
- 不能执行订单。
- 不能创建备份。
- 不能启用 live trading。

第四个问题：完成后怎么证明？

- 后端 API 测试覆盖正常 ready 分支。
- 后端 API 测试覆盖缺字段 blocked 分支。
- 前端测试覆盖 dashboard 渲染 daily status。
- 全量后端测试通过。
- 全量前端测试通过。
- 前端 build 通过。
- Doc Impact 检查通过。
- `git diff --check` 通过。

## 好的输入应该长什么样

一个足够好的输入可以这样写：

```text
为每日工作流增加只读状态中心。

目标：在首页看到当前交易日和策略的数据、因子、候选、复核、
人工计划、执行报告和备份状态。

约束：
- 不新增 SQLite 表。
- 不触发任何任务。
- 不执行交易。
- 必须复用现有 repository 和 candidate API 语义。
- 策略缺字段时显示 blocked 和 missing_fields。
- 完成后更新 workflows 和 api-contracts。
```

这个输入已经足够进入 `specify` 阶段。

## 不够好的输入长什么样

不够好的输入通常只有一句：

```text
帮我做一个每日状态面板。
```

这句话的问题是：

- 没有说明状态包含哪些步骤。
- 没有说明是只读还是会触发任务。
- 没有说明数据来源。
- 没有说明策略缺字段怎么处理。
- 没有说明是否涉及交易。
- 没有说明验证标准。
- 没有说明文档影响。

在 Spec Kit 流程里，这类输入需要经过 clarify。

## Clarify 问题清单

如果当时要正式跑 `/speckit.clarify`，可以问这些问题：

1. 状态中心是否只能展示状态，还是可以触发修复动作？
2. 状态步骤是否固定为数据、因子、候选、复核、计划、执行、备份？
3. 备份新鲜度如何判断，按文件存在还是按 mtime？
4. 策略缺字段是否阻塞整体状态？
5. 没有候选股是 blocked、warning 还是 ready_for_review？
6. 人工计划和执行是否只看当前 trade_date 和 strategy？
7. 前端展示是否放在 dashboard 首屏？
8. 是否需要支持多个账户或多个 broker？

本案例采用的答案：

| 问题 | 答案 |
| --- | --- |
| 是否触发修复动作 | 否，只读 |
| 状态步骤 | 固定七步 |
| 备份判断 | 最新备份 mtime 不早于数据库文件 |
| 策略缺字段 | 阻塞 selected strategy |
| 没有候选股 | warning，但流程可进入复核判断 |
| 计划和执行过滤 | 当前 `trade_date` + `strategy` |
| 前端位置 | dashboard |
| broker 支持 | 不新增 |

完成这些检查后，进入 `02-spec.md`。
